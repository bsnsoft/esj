# What one `esj` process costs

*Part of [EN16931 Semantic JSON](../README.md).*

What one process costs in wall clock and in resident memory, at which heap ceiling it stops
working, and where the cost comes from — the numbers behind the process boundary that
[`deployment.md`](deployment.md#batch-mode-is-not-isolation) states in one sentence, and behind
the start-up cost a long-lived process avoids;
[`validation-measurements.md`](validation-measurements.md) is what the check itself costs once
a process is running. Everything below was measured on one machine, once, with the commands
printed next to the tables. Nothing here is a conformance statement: limits are policy
(`SPEC.md`, sections 3.1 and 12.2).

## The machine and the method

| Property | This machine |
|---|---|
| CPU | Apple M5, 10 cores |
| Memory | 32 GiB |
| Operating system | macOS 26 |
| Java | OpenJDK 21.0.10 (Corretto), 64-bit server VM |
| Date | 2026-09-19 |

One cell is one process, started as a caller would start it:

```text
java -Xmx<ceiling> -XX:+ExitOnOutOfMemoryError -jar esj.jar <command> --limits large <file>
```

Every cell is a **file argument** unless its row says *standard input*; the two are not
interchangeable at the front door, and *The front door* below measures both. The wall clock is
taken around the whole process, JVM start-up and the compilation of the XSLT included. The peak
resident set is what `/usr/bin/time -l` reports: the whole process, not the Java heap, which is
why every figure is well above the `-Xmx` it ran with. **The machine was shared** with other
builds while these ran, at a one-minute load average between 3 and 7 for the large cells. Every
cell that finished was run three times; the **minimum** wall clock and the **median** peak
resident set are reported, never in parallel.

### The budget

`over 30 s` means a cell was killed after **30 seconds**; its peak resident set is still
reported and is a lower bound on finishing. Four such cells were waited out once — `convert`
and `validate` of 50 MB of UBL at `-Xmx512m` and `-Xmx1g`, **6.4 to 8.1 minutes**. Growth,
from the two completed convert cells at `-Xmx1g`: 4.2 MB takes 3.85 s and 52.4 MB 381.9 s, a
factor of 12.5 in the document against 99 in the wall clock, an exponent of about 1.8; along
it 80 MB is on the order of **15 minutes** and 150 MB **45 minutes**, estimates from two points.

## Large documents

Every cell ran with `--limits large` and through the XSLT path, which was the only reader when
these were taken and is `--importer xslt` today; the streaming reader is measured further down.
`over 30 s` is the budget described above, with the resident set the run had reached when it
was killed. Two exit codes appear:

- **exit 3** is not one of the tool's codes: it is what the JVM leaves with under
  `-XX:+ExitOnOutOfMemoryError`, within a second or two, the ceiling having been reached while
  the XSLT processor builds its tree. The exit-code tables list it so that nobody reads it as a
  verdict; the tool's own reserved code for a constrained conversion is 8.
- **exit 7** is the tool's: a bound of this run was met and no verdict was reached.

### Where the time goes at 80 MB

A stack sample 20 seconds into the 80 MB UBL convert at `-Xmx1g` found the process inside a
filter expression of the mapping stylesheet, 19.9 s of CPU in 20.2 of wall clock: compute in the
transformation, not collection, input or the ESJ writer. At `-Xmx4g`, which produced the ESJ
documents the other rows read, 50 MB of UBL takes 368.7 s and 1725 MiB, 50 MB of CII 155.1 s
and 1059 MiB.

## The heap a profile's bounds imply

A bound is a promise that an input of that size is read rather than refused, and reading it
costs at least the bytes. The smallest `-Xmx` at which an input **at** each bound is read and
judged, by a ladder of ceilings, on documents and not on adversaries:

| Profile | Bound | Input it was measured with | File argument | Standard input | Resident set |
|---|---|---|---|---|---|
| default | 4 MiB of XML | 4 177 321 B of UBL, 2 780 lines | `64m` | `64m` | 215 MiB / 210 MiB |
| default | 64 MiB of ESJ | 67 000 000 B: the ESJ of that UBL behind insignificant whitespace | `128m` | `160m` | 291 MiB / 257 MiB |
| default | 64 MiB of PDF | 67 000 003 B: a hybrid invoice padded with a comment before its cross-reference section | `96m` | `160m` | 271 MiB / 285 MiB |
| `large` | 256 MiB of XML | 262 144 000 B: a CII root element around one comment | `3g` | not measured | 3 477 MiB |
| `large` | 512 MiB of ESJ | 536 000 000 B, built as the 64 MiB row | `640m` | `1280m` | 1 259 MiB / 1 308 MiB |
| `large` | 512 MiB of PDF | 536 000 004 B, built as the 64 MiB row | `640m` | `1280m` | 1 240 MiB / 1 230 MiB |
| `large` | content, not a bound | 89 713 067 B of ESJ: 300 000 dense invoice lines, from `conformance/scale`, with `--no-syntax` | `2560m` | not measured | 2 913 MiB |

The last column is the peak resident set of the whole process at the ceilings of the two
columns before it, in that order, and **it is the column a container is sized on**: `-Xmx`
bounds the Java heap alone, at `-Xmx640m` the process occupies about 1.7 times the number on
the flag, and a container given the `-Xmx` figure is killed by the operating system.

The padding is what makes these the *cheapest* inputs of their size: a document at the bound
whose content is real costs what the tables above give it on top. The XML row measures the
XSLT, and `-Xmx3g` is what the cheapest 250 MiB of XML one can write needed there. Every other
row is within a factor of two of the bound; the standard input costs about twice the file
argument. The last row is content rather than padding, and the only cell taken with
`--no-syntax`: `--rules none` has the same floor (`2304m` is out of heap either way) and takes
11.7 s against 22.0 s. Written as CII the document is 348 604 852 B, past the 256 MiB the
profile admits, so the official artefacts cannot run on it at any ceiling and the verdict is
`INDETERMINATE`; `validate` without `--no-syntax` needs `4608m`, 4 713 MiB and 35.2 s.

## The streaming reader at 80 MB

Everything above is the XSLT path of `esj-xr`; `esj-bindings` reads the same two syntaxes from
the binding tables with a pull parser holding one element. Same machine and method, the reader
called directly rather than through the command line:

| Input | Lines | Values | `-Xmx256m` | `-Xmx512m` | `-Xmx1g` |
|---|---:|---:|---|---|---|
| 80 MB CII | 33 432 | 501 521 | 1.82 / 364 | 1.69 / 603 | 1.69 / 606 |
| 80 MB UBL | 55 884 | 838 301 | out of heap / 375 | 2.97 / 607 | 2.67 / 738 |
| 80 MB CII dense | 88 110 | 704 921 | out of heap / 373 | 2.61 / 608 | 2.34 / 602 |
| 80 MB UBL dense | 177 716 | 1 421 769 | out of heap / 380 | out of heap / 648 | 4.33 / 1082 |

Each cell is *wall clock in seconds / peak resident set in MiB*, minimum of three runs, as
above. The same rows through the XSLT path are `over 30 s` at every ceiling, and the two waited
out at 50 MB took six to eight minutes. Three things the table says and one it does not:

- **The reader is not what needs the heap; the document is.** Every cell that ran out did so
  holding values, not XML: the working set is one element deep, and the ceiling follows the
  number of values, roughly 350 to 400 bytes each. 500 000 fit in 256 MiB, 840 000 need 512 MiB,
  1.4 million a gibibyte.
- **The dense class is the interesting one**: 177 716 invoice lines read in 4.3 seconds, but not
  in 512 MiB — a property of the document representation, not of the reader.
- **Peak resident stays 60 to 80 MiB above the ceiling**, against the XSLT path's 130 to 250.
- It says nothing about a *validator* at that size; `docs/validation-measurements.md` does.

## The two writers at 50 and 80 MB

Writing costs more, because a writer builds the whole element tree of the output first:
`esj convert --to cii` and `--to ubl` through the command line, so the figures include reading
the UBL input, building the semantic document, building the tree and serializing it.

| Input | Values | Output bytes | `-Xmx1g` | `-Xmx2g` | `-Xmx4g` |
|---|---:|---:|---|---|---|
| 50 MB UBL → CII | 523 946 | 75 237 643 | 5.1 / 1246 | 4.5 / 1601 | 4.1 / 1653 |
| 80 MB UBL → CII | 838 301 | 120 379 023 | out of heap | 8.9 / 2307 | 9.2 / 3012 |
| 50 MB UBL → UBL | 523 946 | 46 247 372 | 3.5 / 1184 | 3.4 / 1270 | 3.5 / 1461 |
| 80 MB UBL → UBL | 838 301 | 73 994 442 | out of heap | 6.4 / 1881 | 5.9 / 2538 |

Each cell is *wall clock in seconds / peak resident set in MiB*, as above. Three things follow:

- **Writing costs two to three times what reading the same document costs**, and the two
  syntaxes are not the same price: a cross industry invoice of this document is 120 MB against
  the UBL invoice's 74 MB, and it costs about a third more time and heap. A service that
  converts at this size is sized by the writer and by the syntax it writes.
- **The ceiling is the element tree.** The bytes are produced directly and `--max-output-bytes`
  is compared as they are produced, which keeps one full copy of the output out of the peak —
  but the tree is not bounded by that switch, and both writers build it whole. A 140 000-line
  dense document runs out of a gibibyte inside the writer with `--max-output-bytes` standing at
  1 GiB and 76 MB of output ahead of it.
- **Past about a million values a writer wants more than a gibibyte.** The dense series at
  `-Xmx1g` and `--limits large` writes 40 000 lines (0.32 M values) in 1.9 s at 829 MiB and
  80 000 lines in 3.5 s at 1199 MiB, and leaves 140 000 lines with exit 7 and no partial file.
  `roadmap.md` records a streaming writer as the answer rather than a larger `-Xmx`.

## The front door

The default profile refuses the 4 MiB instance:

| Input | Form | Profile | `-Xmx` | Outcome |
|---|---|---|---|---|
| 4 MiB UBL | file | default | `256m` | exit 7 after 0.10 s / 64 MiB |
| 4 MiB UBL | file | `--limits large` | `256m` | exit 0, see the table above |

What a refusal *costs* depends on the form the input arrived in: a file is refused on the
length the file system reports, a stream is collected until one byte past the bound. Both
bounds of the `large` profile, in both forms:

| Input | Bound it is past | Form | `-Xmx` | Outcome |
|---|---|---|---|---|
| 450 MB UBL | 256 MiB of XML | file | `256m`, `512m`, `1g` | exit 7 after 0.10 s / 65 MiB |
| 450 MB UBL | 256 MiB of XML | standard input | `1g` | exit 7 after 0.21 s / 581 MiB |
| 450 MB UBL | 256 MiB of XML | standard input | `512m` | exit 7 after 0.22 s / 451 MiB |
| 450 MB UBL | 256 MiB of XML | standard input | `256m` | exit 3, an empty error stream |
| 600 MiB ESJ | 512 MiB of document | file | `512m`, `1g` | exit 7 after 0.09 s / 65 MiB |
| 600 MiB ESJ | 512 MiB of document | standard input | `1g` | exit 7 after 0.24 s / 845 MiB |
| 600 MiB ESJ | 512 MiB of document | standard input | `512m` | exit 3, an empty error stream |

Every refusal names the bound and the switch that raises it. **From a file a bound costs
nothing to enforce; from a stream it costs about twice the bound in resident set**, and a heap
that cannot hold that much answers with the crash instead of the refusal — and the standard
input is the form [`deployment.md`](deployment.md) recommends from a service.

## Start-up

What a process costs before it has read anything, and what the packaging takes off it. The 3 kB
of ESJ is `examples/standard-invoice.esj.json` (3 355 bytes), the 7 kB of UBL
`conformance/kosit/business-cases/standard/01.01a-INVOICE_ubl.xml` (6 742 bytes), the PDF
`conformance/pdf/factur-x.pdf`.

### On Java 21, with the jar and an AppCDS archive

Median of five runs, in seconds; the resident set is of the `validate` column.

| Start-up | `--version` | `get /BT-1`, 3 kB ESJ | `validate`, 7 kB UBL | RSS |
|---|---|---|---|---|
| default | 0.094 | 0.112 | 0.402 | 151 MiB |
| `-XX:TieredStopAtLevel=1` | 0.088 | 0.103 | 0.328 | 126 MiB |
| AppCDS, archive from `--version` | 0.087 | 0.104 | 0.401 | 149 MiB |
| AppCDS, archive from a `validate` run | 0.092 | 0.099 | 0.300 | 138 MiB |
| both, archive from a `validate` run | 0.084 | 0.092 | **0.231** | 115 MiB |

**How the archive is made decides whether it is worth anything**: one recorded from `--version`
saves nothing on the path that matters, one recorded from a real `validate` takes a quarter off
it, and the two together take 43 % off the smallest useful run. The archive is 19.7 MB and is
tied to the exact JDK that wrote it.

```text
java -XX:ArchiveClassesAtExit=esj-cds.jsa -jar esj.jar validate \
    conformance/kosit/business-cases/standard/01.01a-INVOICE_ubl.xml
java -XX:TieredStopAtLevel=1 -XX:SharedArchiveFile=esj-cds.jsa -jar esj.jar validate <invoice>
```

Minimum wall clock of five runs (seven for the two small commands), median peak resident set,
2026-09-21, at a one-minute load average between 8 and 40: read the differences, not the
absolute numbers, and not against the Java 21 table above, which was taken on another day at
another load. *As shipped* is `bin/esj`, which adds `-Xms32m -Xmx512m` to the row above it.

| Java 25 | `--version` | `get /BT-1` | `validate`, UBL | RSS | `validate`, PDF | RSS |
|---|---|---|---|---|---|---|
| the jar on a JDK 25 | 0.12 | 0.15 | 1.41 | 296 MiB | 0.77 | 231 MiB |
| runtime image | 0.16 | 0.18 | 1.31 | 283 MiB | 0.81 | 252 MiB |
| with `-XX:+UseCompactObjectHeaders` | 0.16 | 0.18 | 1.04 | 264 MiB | — | — |
| with the AOT cache as well | 0.11 | 0.13 | 0.64 | 248 MiB | 0.43 | 212 MiB |
| runtime image as shipped | 0.10 | — | **0.50** | 203 MiB | — | — |
| native executable | 0.00 | 0.00 | **0.12** | 110 MiB | 0.10 | 121 MiB |

**Both packaged defaults pay.** Compact object headers take 20 % off the smallest useful run and
16 MiB off its resident set at no cost, and the ahead-of-time cache of JDK 25 — 45 MB, written
by one training run over a PDF validation at package time — takes another 38 %. The two are one
setting: a cache recorded with compact headers is refused, loudly, by a virtual machine running
without them, so the launcher passes them together.

```text
java -XX:+UseCompactObjectHeaders -XX:AOTCacheOutput=esj.aot -jar esj.jar \
    validate conformance/pdf/factur-x.pdf
java -XX:+UseCompactObjectHeaders -XX:AOTCache=esj.aot -jar esj.jar validate <invoice>
```

**The native executable starts in no time and is the slower one on a big document**, which is
the trade a compiler that never warms up makes:

| 50 MB of UBL, `convert --limits large --to esj`, `-Xmx4g` | Wall clock | RSS |
|---|---|---|
| runtime image | 2.39 s | 854 MiB |
| native executable | 6.12 s | 455 MiB |

So: the executable for the ordinary document, where the whole run is start-up, and the runtime
image where a document is large enough for the just-in-time compiler to earn its warm-up
([`install.md`](install.md)).

## Rendering

`esj render` is the one command whose cost is in what it writes: a PDF is assembled whole in
memory, so the cost follows the pages, and one value of a megabyte in a narrow column is close
to three hundred of them. Each cell is *wall clock in seconds / peak resident set in MiB*, one
run at a load average between 2.6 and 15: read the times as an order of magnitude.

| Document | Rendering | `-Xmx256m` | `-Xmx512m` | `-Xmx1g` | `-Xmx2g` |
|---|---|---|---|---|---|
| `examples/standard-invoice.esj.json`, 81 values on 1 page | PDF | 0.6 / 133 | 0.6 / 135 | — | — |
| the same | HTML | 0.8 / 173 | — | — | — |
| 10 000 lines, 150 041 values, 7.8 MB of ESJ → 1251 pages, 2.3 MB | PDF | 93.6 / 381 | 67.2 / 620 | 65.1 / 614 | — |
| the same → 132 MB of HTML | HTML | exit 3 after 1.2 s / 374 | exit 3 after 2.6 s / 693 | 3.1 / 1182 | 3.4 / 1321 |
| 20 lines carrying 1000 kB of text each → 21 MB of ESJ, 5773 pages | PDF | — | 97.1 / 616 | 95.0 / 617 | — |
| 50 lines carrying 1000 kB of text each → 51 MB of ESJ, 14 430 pages | PDF | — | exit 7 at 300 s / 642 | — | exit 7 at 300 s / 779 |
| the same, with `--max-runtime 20m` | PDF | — | 338.5 / 658 | — | 330.9 / 846 |
| one invoice number of 500 000 digits → 0.5 MB of ESJ, 213 pages | PDF | — | 248.0 / 604 | — | — |

Five things follow:

- **An ordinary invoice renders in well under a second in 256 MiB**, either way.
- **The PDF is slow where the HTML is fast, and the HTML is large where the PDF is small.** Ten
  thousand lines are a minute and 1251 pages of PDF, or three seconds and 132 MB of HTML.
- **A rendering can be far larger than the document it renders**, and it does not take a large
  document: every bound of `--limits` is about the input. The wide rows sit inside the default
  profile and cost minutes and hundreds of megabytes at six and fourteen thousand pages, and
  the last row is half a megabyte — one invoice number of 500 000 digits, laid out once per
  page because BT-1 is the title and the footer, 213 pages and 248 seconds.
- **Two things stop a runaway rendering: the clock, and a bound on the output.** `esj render` arms
  `--max-runtime` at five minutes where the caller named none, which ended the 50-line document
  with exit 7 and no file; a heap that runs out ends it with exit 3. `--max-pages` bounds what the
  renderer produces rather than what it is given: a rendering that reaches it leaves with exit 7.

## What the numbers say

- **`-Xmx512m` is enough** for documents of ordinary size, `-Xmx256m` for everything the
  conformance corpus contains.
- **Size the container by the resident set, not by `-Xmx`**: a run that fills its heap ends up
  to about 200 MiB above the ceiling (measured +86 to +192 MiB), because the jar, the metaspace,
  the compiled code and Saxon's structures are outside it.
- **An out-of-heap death is exit 3**, within a second, with the JVM's notice on the **standard
  output** and an empty error stream — the native executable writes its notice to the error
  stream instead. A caller treats either, and every code outside the table, as a crash.
- **The XSLT bootstrap is the ceiling, not the heap and not the format**: 50 MB through it costs
  minutes, where the streaming reader — the default of both the command line and the API —
  reads 80 MB in two to four seconds.
- **Above that class, let the bound refuse the document**: the large profile's 256 MiB input
  bound answers a 450 MB file in a tenth of a second with exit 7 and names the switch that
  raises it.

## Reproducing this

```text
mvn -B -DskipTests package

python3 conformance/scale/generate.py \
    --source conformance/kosit/business-cases/standard/01.01a-INVOICE_ubl.xml \
    --target-bytes 50M --out conformance/scale/out/ubl-50mib.xml

/usr/bin/time -l java -Xmx1g -XX:+ExitOnOutOfMemoryError -jar esj-cli/target/esj.jar \
    convert --limits large --to esj conformance/scale/out/ubl-50mib.xml > /dev/null
```

The *Rendering* documents come from the same generator: `--lines 10000` for the one of 150 041
values, `--text-bytes`, which pads the item name of every line, for the wide ones:

```text
python3 conformance/scale/generate.py \
    --source conformance/kosit/business-cases/standard/01.01a-INVOICE_ubl.xml \
    --lines 20 --text-bytes 1000k --out conformance/scale/out/ubl-20-wide.xml

java -Xmx4g -jar esj-cli/target/esj.jar convert --limits large --to esj \
    conformance/scale/out/ubl-20-wide.xml > conformance/scale/out/ubl-20-wide.esj.json
```

The row of the 500 000-digit invoice number is `examples/minimal.esj.json` with `/BT-1`
replaced by that many digits; `conformance/scale/README.md` has the generator's other sizes.
Every table above *Rendering* ran its own last line for every combination of input, ceiling and
command, three times where it finished; the *Rendering* rows are one run each.

A test in `esj-cli` pins the *outcomes* of the smallest rows by spawning the jar as a caller
does: the corpus converts at `-Xmx256m`, an input past the default bound leaves with exit 7, a
heap too small with exit 3. The timings belong to this machine and are asserted nowhere.
